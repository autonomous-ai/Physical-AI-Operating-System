01 / An AI-native robotic OS

A companion in the room.
An executive for your agents.

Lamp senses what is happening, talks naturally, acts through a dependable local body, and delegates substantial work to agents on your computers.

One loop, different speeds. Gemini handles fast conversation; local code handles immediate reflexes. Jev is the pluggable policy model for higher-level choices. Rust coordinates execution, and Harness carries delegated work to agents on your computers.

How the classic agent–environment loop maps to Lamp

The useful distinction is between what Lamp observes and what Lamp believes is happening. A sensor reading cannot reveal the complete world state or a person’s intent. Lamp estimates its situation from observations and history. This follows the state/observation distinction in OpenAI’s RL introduction.

ConceptMeaning for Lamp
AgentLamp as a complete system: body, local runtime and the model services it uses. Remote workers are delegated agents with their own execution loops.
EnvironmentThe desk, room and people around Lamp, plus connected computers and the digital systems it can affect. The environment also changes independently of Lamp.
Observations / topicsTimestamped sensor and perception messages, conversation events, and task or device receipts. A topic is the delivery channel; its messages supply observations.
State / current situationAn estimate built from fresh observations, recent history, memory, Lamp’s body state, active goals, ongoing tasks and permissions. Preserve uncertainty and freshness; a list of topic names is not this state.
PolicyThe rule for choosing what to do from the current situation and goal. Jev implements the main semantic choice within the existing Rust executive; fast conversation and local reflexes keep their own paths.
Actions / service callsThe eligible service catalog defines the executive’s action space. An action is a selected invocation with validated parameters, possibly part of an explicitly coordinated sequence. Waiting or abstaining requires no service call. Streaming speech remains a separate fast path.
Feedback / rewardObserved outcomes feed the next decision. A scalar reward is needed if we choose an RL training objective; an API success flag or a user’s inferred mood is not automatically that reward.

Two public interface families still suffice. Topics distribute observations and events. Services request quick calls, tracked device operations or durable agent tasks. A service’s acceptance is distinct from completing the action.

The loop is asynchronous. Sensors have different rates, meaningful events trigger decisions, and active operations continue under their own controllers. Lamp does not wait for every sensor or a cloud decision before the next audio frame or local stop.

The first environment: beside the user’s monitor

The initial product setting is a stationary Lamp on the user’s desk, to their left or right. Define left/right from the seated user facing the monitor. Record placement and a calibrated neutral facing direction during setup; a placement label alone does not establish motor coordinates or clearances.

Represent relevant relationships: where the user is relative to Lamp, whether they may be addressing it, current light and body state, and what work is running. Use configured or measured geometry where available. Unknown desk edges, occluded people and unavailable sensors stay unknown.

Observe: The user asks, “Ask my coding agent to review this change.”

Estimate state: Lamp is being addressed, a paired computer is available, and a target agent and task context can be resolved.

Choose: Jev selects the offered delegation action; missing context instead offers clarification.

Act: lampOS validates the request and invokes the agent-task service through Harness.

Observe again: Acceptance, progress or a question updates task state. Lamp reports the actual result when it arrives.

This is a design scenario. It does not assume screen access, identity, permission or task success from physical presence alone.

04 / Our adaptation of ROS

Two interface families.
Three kinds of service work.

Topics tell interested consumers what happened or what is currently observed. Services ask a component to answer a question or perform work.

Topics

Async publish / subscribe

Examples: audio chunks on mic2, frames on camera, a tracked person on people, a touch gesture, or a task result.

Several consumers can independently subscribe. Producer cadence and each consumer’s freshness needs are explicit.

Services

Request / result APIs

Examples: read brightness, follow this person, ask an agent to research a topic.

“Service” is our broad API vocabulary. A service can expose all three contracts below and publish its own topics.

Why not send everything to an agent?

An agent can choose to call follow_person. The installed controller still needs to track smoothly, handle disappearing targets, arbitrate the motor and stop without a cloud round-trip. V1 already uses this pattern in several places.

Use agent reasoning where open-ended planning helps. Keep timing, repetition, permissions and hardware bounds in code.

What we borrow beyond pub/sub

Typed interfaces, independent consumers, freshness and queue policies, component lifecycle, capability discovery, goal IDs, cancellation, feedback, simulation and traceable execution.

No mandatory DDS/ROS runtime is proposed. Start by extending existing Rust IPC; implement only the contracts Lamp needs.

05 / The living observation graph

One observation can feed several consumers.

Named topics carry sensor streams and derived observations. Any number of authorized consumers can subscribe; each consumer can combine several topics. A subscription does not require a model call for every message.

Publish once. Let each consumer listen.

The same mic2 stream can feed Gemini Live, Deepgram and local voice detection. The same camera can feed tracking, recognition and scene understanding. Each subscription runs independently.

Consumers can publish new topics.

A camera frame is an observation; a tracked person or recognized identity is a derived observation. Both use the same pub/sub pattern.

Voice keeps its direct path. mic2 → active voice adapter → speaker. Gemini Live does not wait for Deepgram, a transcript, Jev or another subscriber. Topic names and consumer lists are proposed contracts. Rates are profile-dependent, not measured guarantees. Acquisition, inference, context updates and decision calls have separate budgets. Remote agents receive authorized projections through an adapter rather than unrestricted access to the device bus.

Latest observations

Presence, body state and environmental values can coalesce. Expire stale values; detect gaps. A slow subscriber must not hold the producer.

Ordered events

Physical edges and conversation segments preserve causal identity. An overflow invalidates an incomplete gesture or marks a transcript gap.

Durable outcomes

Accepted tasks, questions and terminal results need persistent records. A topic notification helps discovery; status lookup repairs a missed event.

Resource and timing rules
  • Bound each subscription, inference queue and in-flight decision count. Publish queue loss, deadline misses and source health rather than silently accumulating old work.
  • Use monotonic local deadlines; carry remaining duration across hosts. Wall-clock timestamps and remote clock uncertainty describe evidence rather than create false timing precision.
  • Keep units and coordinate frames explicit. “Turn toward this person” requires a current track transformed into the qualified motor frame, not an unlabelled image coordinate.
  • Revocation reaches the enforcing worker directly. The privacy topic is a state mirror for consumers, not the only enforcement path.
  • Give each consumer a minimum necessary projection. Memory, agents and model providers do not gain access to every frame, identity or conversation just by subscribing.

07 / Jev’s place in the brain

The model chooses.
The executive makes it real.

Jev replaces a decision-making role previously handled by the main agent. It does not replace the agent engine that carries out open-ended work.

Policy is the role; Jev is the proposed first model in that role. The executive supplies the situation, goal and eligible service choices. Jev selects a choice or abstains. Rust revalidates and dispatches it. This names the existing decision boundary; it adds no new runtime layer.

Should Lamp’s policy be a neural network trained with reinforcement learning?

A policy can be implemented in code or by a learned model. Neural networks are well established as policy implementations; reinforcement learning is a way to train a policy using rewards. Choosing an action with a deployed model and updating that model’s weights are separate operations. OpenAI: RL concepts and policies.

Robot policies also learn from demonstrations. Diffusion Policy learns visuomotor behavior through imitation and generates action sequences. Physical Intelligence’s π*0.6 / RECAP combines demonstrations, collected experience and expert interventions with RL. A neural policy therefore does not imply that every deployed Lamp must experiment and learn online.

Separating high-level choices from execution has useful research precedents. SayCan combines language-based skill selection with estimates of whether those skills are feasible. Gemini Robotics 1.5 pairs a reasoning model with a model that performs physical actions. These are architecture examples, not Lamp benchmarks or a proposal to replace Gemini Live with Gemini Robotics.

Supervise useful progress and complete worker generations

The proposed supervisor gives each worker its own progress deadline and recovery state. A stuck camera teardown must not stall speaker or motor supervision. After a supervisor crash, the outer service manager must verify teardown of the entire previous worker generation/cgroup before replacements acquire device access. Unresolved ownership stays quarantined; a heartbeat alone is not proof of useful progress. Current Rust still has blocking child-wait paths; complete lifecycle isolation remains implementation work.

Real-time discipline without a new kernel project

Keep the supported Linux base and existing Rust worker boundaries. Use fixed-capacity media/control storage, short critical paths and independently supervised blocking work. Measure scheduler contention and driver stalls before considering PREEMPT_RT or a separate controller.

Rust memory safety, a short loop interval and expiring leases do not establish hard real-time guarantees. A lease only enforces when its worker runs; a Linux process cannot prove an independently wedged actuator has stopped. Qualify actual board, firmware and physical behavior.
