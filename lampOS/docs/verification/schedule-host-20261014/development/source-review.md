## What V1 actually implements

### Shape, time computation, and origin

`system/schedule/store.go:36` defines a Schedule with ID/name/instructions/enabled, kind, connector requirements, cadence, revision, optional end time, next run, and local last-run bookkeeping. `KindSpeak` sends literal text through `AgentGateway.Speak`; blank or **unknown** kind resolves to an agent prompt (`store.go:26`, `runner.go:244`). These are two different effects, neither a dedicated countdown object.

`system/schedule/spec.go:13–50` supports daily, weekly, monthly, interval, once, and manual. Daily/weekly/monthly use local `HH:MM`; `Times` takes precedence over legacy `Time`, with every selected time combined with weekly days. Local authors may supply up to 12 times (`intent.go:195`). Weekdays 0 and 7 both mean Sunday. Monthly days 29–31 clamp to the month's last day. `NextRun` is strictly after the supplied instant; `At == after` is spent, and a next occurrence equal to `EndAt` is allowed (`spec.go:53`, `:148`, `:185`, `:228`). Manual and unknown cadence do not automatically run.

Daily/weekly/monthly receive a deterministic device-and-schedule jitter of **−300 through +299 whole seconds** (`spec.go:236`). Intervals and once are not jittered. `DejitterAnchor` reverses that offset before finding the next occurrence, preventing negative jitter from repeatedly selecting the same slot. Interval math is `after + EveryMs` with a five-minute floor; local validation refuses under-floor intervals, while runner math clamps them (`spec.go:210`, `intent.go:238`). This floor protects paid agent calls; it is not evidence of an appropriate minimum for a person's countdown.

Wall-clock calculation uses Go `time.Date` and an IANA location. Blank/invalid zones fall back to UTC; bad zones are warned during sync but retained as the stored string (`sync.go:9`, `store.go:297`). There is no explicit unsynchronized-clock gate in this scheduler. Serialized `NextRunAt` is a wall instant, not a restart-stable monotonic deadline. DST tests at `spec_test.go:44` and `:67` assert one occurrence on the transition day and the next on the following day; they **do not select a particular resolution of the nonexistent 02:30 or ambiguous 01:30**. A current UTC offset alone cannot reproduce the recurrence policy.

The backend owns the full confirmed list: `system/server/device/delivery/mqtt/schedule_sync_handler.go:13`. Device create/update/delete are separate persisted intents, not executable schedules. An intent carries a random 128-bit key reused across retries and a backend revision for edits (`system/schedule/intent.go:16`, `:52`). HTTP create returns 202/pending after recording and trying to publish the intent (`schedule_crud_handler.go:28`, `:88`). MQTT retries do not drop the intent; either applied or rejected acknowledgement removes it (`schedule_mutate.go:29`, `:52`, `:68`). Thus local persistence of a V1 create is not confirmation that the reminder is scheduled. No first-class snooze, countdown, or natural-language date parser was found in the inspected `system/schedule`, its schedule handlers, or named reminder/timer entry points in HAL/runtime code; arbitrary agent-runtime facilities are outside this review.

### Due work and failure

`system/schedule/runner.go:83` runs one tick immediately at startup, then every minute. The due loop skips disabled/not-yet-due/unseeded items. An occurrence more than 30 minutes late is moved forward **without firing or recording a run**; a spent one-off is cleared (`:110`, `:179`). Exactly 30 minutes is still within catch-up. This is materially different from task 6's requested late delivery after downtime.

Busy gateways defer an occurrence unchanged until another tick. Items are processed sequentially, checking busy each time; the single-flight test relies on the gateway setting busy on its first send (`runner_test.go:405`). This is not an independent transaction lock across manual `RunNow` and the ticker. Missing required connectors produce a skipped outcome even while busy; success and skip advance the occurrence, failure does not (`runner.go:128`, `:138`, `:190`). A failed send is retried each tick inside the catch-up window, with only the first failure report for that occurrence; success after failure still reports. The next interval is based on the previous scheduled occurrence, not delivery completion, so several nearby missed interval slots can be caught up over successive ticks. Manual RunNow updates last-run fields without moving the scheduled next time (`:225`).

`RunReport` explicitly calls `SendLatency` handoff latency and says success means handed off, **not completed or heard** (`runner.go:29`). The agent path adds `[via:schedule]`; speak sends the instructions literally. Handoff occurs **before** recording the result. A crash or store failure after handoff can leave the occurrence due for another send; persistence errors are logged but the success report still carries the computed next time (`:194–221`). There is no durable speech-receipt acknowledgement or occurrence idempotency key across the speaker boundary in this runner. The generated attempt ID is log correlation only (`:244`).

### Storage and arithmetic pitfalls visible in source

- `system/schedule/store.go:97–155`: missing/corrupt data becomes empty; `Load()` also discards read errors. `LoadChecked()` distinguishes unreadability but still treats invalid JSON as empty. This behavior is intentionally asserted by `store_test.go:59`; it is not proof that pending reminders survive corruption.
- `store.go:120`: a same-directory temporary file is written, closed, and renamed. There is **no file sync or directory sync**. The atomic-replace test at `store_test.go:11` covers failure before rename in a read-only directory, not power loss. The mutex is process-local, not a second-process exclusion mechanism. No schedule-count/file-size bound is enforced here.
- `sync.go:32–58`: full list/zone replacement is one write, then next times are seeded in separate writes. Per-item seeding failures are logged and overall sync still succeeds. Sync recomputes from now, so a freshly synced past once item is treated as spent (`sync_test.go:29`), rather than recovered as late. Zone changes resync from now through `timezone_set_handler.go:54`.
- `spec.go:219` and `intent.go:242`: unsigned milliseconds are converted/multiplied into signed `time.Duration` without a checked upper bound. Large durations can wrap before floor comparison. `NextRunForDevice` applies jitter **after** `Spec.NextRun` checks end time (`spec.go:258`), so positive jitter can move the returned instant beyond `EndAt`. These are source-derived boundary risks, not newly reproduced failures.

Useful authored regressions to reread when the task is claimed: `spec_test.go` (strict boundary, DST day uniqueness, Sunday, month/leap clamp, interval floor, end time, jitter reversal); `times_test.go` (multiple times, cross product, one next result after a long gap); `runner_test.go:180`, `:218`, `:247`, `:273`, `:307`, `:332`, `:355`, `:379`, `:405`, `:462` (retry/report dedup, no repeat occurrence, busy/catch-up/manual); `kind_test.go:209` (failed literal speech does not burn the occurrence); `store_carry_test.go` (history retained across sync); `requires_test.go` (skip semantics). None demonstrates actual acoustic delivery or durable power-loss recovery.

## Current Rust integration contracts

### Memory and tools sockets

`lampOS/crates/memory/src/protocol.rs:22`, `:66` defines a tagged `op` JSON request enum with unknown fields refused and a 64 KiB line limit. Response shapes distinguish success and coded refusal; request logs omit private text. `memory/src/server.rs:93` refuses non-socket path occupants and a live socket, binds privately before exposing mode 0600, and uses a `ready` file. It serves one connection at a time (`:193`). Each whole request and answer has its own two-second cumulative budget (`:249`, `:299`); oversized input is drained within bounded memory. An EOF can complete a final non-newline request (`:279`), whereas Actions requires a newline. One silent client can delay the next client's work. Tests in `memory/tests/server.rs:141`, `:288`, `:339` cover framing/errors, silent/partial/nonreading clients, privacy in logs, and socket replacement. `memory/tests/binary.rs:193` is an authored killed-process/restart test.

Memory's legacy store takes an exclusive directory lock, uses private files and syncs successful append data (`memory/src/store.rs:438`, `:470`, `:587`). The opt-in days backend is separate SQLite storage with explicit transaction/durability configuration (`memory/src/days.rs:145–165`). These are concrete persistence examples; Schedule is still required to own its own records and cannot read Memory files.

`lampOS/crates/actions/src/server.rs:19` serves `tools.json`, `call.sock`, and `ready`. Its socket is mode 0660; it processes one request/connection at a time, 8,192-byte request cap, one-second read/write socket timeouts, 50 ms accept polling, and two-second catalogue refresh (`:23`, `:43`, `:62`, `:104`). This is a different permission/deadline shape from Memory, not one universal socket protocol.

Voice reads one executive catalogue for each new provider session (`voice/src/tools.rs:205`, `:236`); at most 32 total tools, catalogue at most 64 KiB, unique validated names/descriptions/parameter objects, and reserved Voice/Memory names excluded. Its call shape is `{"op":"call","name":...,"args":...}`, with no transaction key (`:309`). Executive reply line is at most 8,192 bytes and the JSON passed to the model must fit the provider's 4,096-byte tool budget (`:326`, `:334`; `gemini/src/lib.rs:55–63`). `ToolDesk` admits at most eight pending Executive/Memory calls onto individual threads; a held answer executes neither kind, and a reply is delivered only to its originating provider session (`provider_worker.rs:1198`, `:1251`, `:1306`). Calls are not automatically retried. Failure to receive a reply does **not** establish whether a mutation happened.

The advertised ask deadline is 1.5 s. Source nuance: `tools::exchange` starts a deadline before **blocking** `UnixStream::connect`, then sets per-socket timeouts before `write_all`/`read_until`; those compound operations do not recheck the remaining total between their internal reads/writes (`tools.rs:334–361`). Actions similarly uses a socket read timeout around one `read_until`. Memory's explicit chunk loop does recheck its total budget. No slow-drip/connect-backlog experiment was run; the existing pattern is not by itself proof of a hard total deadline.

### Voice-initiated speech and clock

`voice/src/speak_up.rs` is arrival-specific, not a generic reminder API. Presence must be near for three seconds, after five minutes away; a loss under 20 seconds is looking away. It requires 30 seconds without talk and a 20-minute greeting cooldown (`:66`). Presence-file checks run every 250 ms and require mtime age below 1.5 s and finite face height >=0.14 (`:129`). `LAMP_EYES_PRESENCE_FILE` opts into observing, and `LAMP_SPEAK_FIRST=on` opts into speaking; otherwise a due hello is recorded only (`:26`, coordinator `:3618`). These thresholds are greeting policy, not timer-delivery requirements.

The current coordinator's admission site requires no reply, an empty provider queue, no input stream owner/submission drain, fresh listening readiness, and a ready provider session (`voice/src/coordinator.rs:3618`). `commit_written_turn` at `:3987` admits a new owned turn, plans speech, records input admission, queues `ProviderInput::Written` with microphone generation, immediately ends the synthetic input, and lets normal reply/playout own output. It does not report that the note was heard. `turn-owner/src/types.rs:304` makes listening readiness require fresh authority, microphone permission, capture lease, and admission lease; `controller.rs:156` and `:202` enforce input readiness again. Therefore this existing route does not bypass privacy just because it originated locally. No Schedule consumer/receipt path is present in the inspected Voice interfaces.

`voice/src/local_time.rs:73` reads offsets from `/etc/localtime` TZif tables for a supplied Unix instant. It refuses dates beyond listed transitions when a POSIX DST rule remains (`:91`); it does not implement that rule. `offset_here`, `told_here`, and `now_here` read SystemTime and the local file (`:193–225`). `the_time` is default-off, answered immediately in Voice, and returns current local time in words or an error (`tools.rs:179–199`). There is no local-civil-to-instant API, future timezone recurrence engine, IANA zone identity output, or NTP trust assertion here. Its table/DST/refusal and wording tests are at `local_time.rs:268`, `:304`, `:327`.

Health exposes `BoardState.clock_synced: Option<bool>` using the presence of `/run/systemd/timesync/synchronized`, false when its directory exists without the file, unknown without the directory (`health/src/board.rs:463`; `docs/health.md:165`). This is the inspected evidence boundary, not an independently verified clock error or an assertion about all possible time daemons. The current workspace already declares Jiff 0.2 in Surround (`crates/surround/Cargo.toml:32`); no library selection or maintained-source review is made here.

### Bus and health boundaries

`bus/src/wire.rs:34` distinguishes transient Event from one retained Latest value. No Event history is kept. Latest overwrites the preceding value; it is not an acknowledged queue. Publishing counts datagrams accepted/dropped/removed and never establishes application consumption (`bus/src/publish.rs:410`). Latest persistence errors can be reported once and suppressed on later repeats (`:422–442`), so `Ok(Published)` is not a durable due-delivery receipt. The default root is under `/run`, and the message cap is 60,000 bytes (`bus/src/lib.rs:155`, `wire.rs:20`).

The header supplies publisher instance, sequence, caller monotonic timestamp, wall timestamp, and optional lifespan. Expiry is judged from wall time with 50 ms grace (`wire.rs:43–82`); publisher liveness defaults to three seconds with explicit `alive()` for silent topics. A Latest value can be returned with `expired=true`. Source loss, publisher restart, dropped messages, and wall-clock steps are therefore separate facts from a reminder being due or delivered. Bus header `at_us` is whatever the caller provided, not sufficient proof of shared monotonic origin. These facts constrain the task's “survives Voice busy/down” requirement; the bus does not supply it automatically.

`msgs/src/lib.rs:549` provides `Diagnostic {level,name,message,values}`; declaration is a one-second Event at `:591`. Health tracks per-part arrival age, normally stale after five seconds (`docs/health.md:95`). Schedule will need its own truthful report; neither presence of a socket nor merely publishing due work proves speech readiness or completion.

## Open boundaries, deliberately not resolved here

1. Task 6's never-lost late reminder requirement versus V1's 30-minute discard/recurrence catch-up, five-minute interval floor, and ±five-minute jitter. A short timer's precision and repeated-reminder backlog semantics are not specified by those V1 values.
2. The authoritative wall-clock/zone source, unsynchronized startup, forward/backward steps, timezone changes, DST gaps/folds, and relative timers across process restart versus reboot. Voice's current offset formatter does not resolve these questions.
3. Which receipt ends a due occurrence: durable admission, Voice turn acceptance, first accepted speaker write, finished playback, or explicit acknowledgement. Crashes between any two boundaries can produce uncertainty. Cancellation, snooze, and duplicates need an occurrence identity independent of bus sequence and provider session.
4. Whether scheduled speech waits through physical/software input inhibition, a busy room, unavailable provider, and user interruption; what is said after a long absence. Existing hello policy is not a decision on reminder urgency.
5. Where the model's new functions are routed: Voice currently knows one Executive catalogue/socket plus its explicitly special-cased Memory/clock tools. New Schedule socket/Bus types and First's owner integration are unwritten. No supplied API yet defines retry idempotency, list pagination, limits, or permission sharing between service users.
6. Corruption/full-disk/failed-sync behavior, process exclusion, record/pending bounds, strict input validation, and privacy of reminder text in bus consumers and logs. Existing implementations provide examples with different guarantees; none proves this future service's guarantees.
