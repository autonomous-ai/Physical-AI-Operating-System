# V1 capability inventory and Rust migration requirements

12 October 2026. Design and source research only. No implementation, deployment,
commit, device access, or private backup inspection was performed.

The migration should preserve useful behavior and private user state, not the
shape of the Go/Python services. V1 already has a distributed agent system,
local reactions, substantial device operations, and more than one kind of
durable work record. A Rust voice loop alone does not replace it.

This inventory extends the [V1 brain audit](../v1-brain-audit.md), rather than
repeating its detailed voice/attention analysis. Read
[agent engines](agent-engines.md) for the proposed swappable engine boundary and
the [ROS study](ros2-design-study.md) for observation/action separation. Jev has
several different jobs below; none is the full agentic engine. Its deeper audit
is in the [decision-model study](decision-models-study.md).

Decisions are recommendations for planning, not launch commitments:

- **Retain V2:** keep its existing Rust boundary/behavior and extend only the
  missing requirements; this does not assert full V1 parity.
- **Port behavior:** implement the user-visible behavior in Rust, using V1 as a
  reference and test oracle where appropriate.
- **Redesign boundary:** retain the capability with an explicit contract,
  ownership and failure model; do not embed the legacy server or HAL in lampOS.
- **Defer:** advertise the capability as unavailable and preserve migration
  options/private state. This is not permission to delete it.
- **Retire implementation:** remove a coupling or mechanism once its replacement
  passes acceptance; do not silently retire the capability.

Launch labels: **L** is recommended before unattended V2 replaces V1's core
voice/agent/lamp service; **C** is mandatory if that sensor, actuator, channel or
integration is offered at launch; **D** is an explicit initial-release deferral.
Whether motion and each optional sense launch is still an owner decision. A
deferred actuator must be disabled, not reachable through an unqualified tool.

## Findings that change migration order

1. **Service continuity is a release blocker.** Current R still stops serve
   after terminal provider output settles and records `automatic_retry:false`
   (`R:lampOS/crates/live/src/coordinator.rs:2825`). B has transcript fallback,
   provider reconnect and process supervision; these are separate recovery
   layers, not one retry switch. The proposed Deepgram → engine → Gemini TTS
   fallback needs independent qualification, including shared quota failures.
2. **Observation loss is different from restrained behavior.** B couples sound
   checks to camera frames, uses a shared two-worker perception pool, and can
   discard semantic observations at several response gates. Preserve fresh
   situation state before deciding whether to reason or speak.
3. **“Success” needs a stronger definition.** B schedule success is successful
   dispatch, and hardware-marker success can be HTTP acceptance/ignored output.
   Task execution, action completion and audible delivery need distinct states.
4. **Some durable machinery is already good precedent.** Harness reserves and
   binds results, records correlated outcomes before advancing replay cursors,
   and protects uncertain deliveries. External-history journals also preserve
   uncertainty. Do not replace these with a single in-memory task queue.
5. **State migration is a separate deliverable.** Config, persona, biometrics,
   per-person logs, schedules, trust and calibration have different owners and
   lifetimes. A copy of `MEMORY.md` is not a device migration.
6. **Carry current privacy fixes forward.** H adds owner authentication to media
   reads, local-only person detection, recent-speech checks on realtime look,
   and restart-aware snapshot pruning. These are required replacement behavior,
   not evidence that B already provided it.
7. **Keep the useful existing Rust cores.** R interaction explicitly consumes
   already admitted input; camera provides bounded frame/grant ownership;
   environment is a fixed-size state core without drivers; motor control is
   selected and qualified rather than unrestricted full-body parity. None is
   an agent runtime, addressee detector, or complete V1 port.

## Private migration manifest to implement before cutover

Do not read private device data as part of planning. The future importer should
first produce a redacted, owner-reviewed inventory on the authorized device or
backup host. It needs class-specific rules:

| State class | Required migration/deletion treatment |
| --- | --- |
| Device configuration | Preserve the original config and versioned migration report; distinguish explicit values from profile/env/code defaults. Transactional write, rollback and idempotent re-run. Never print key values. |
| Device/backend identity | Preserve or explicitly re-register device identity; simultaneous V1/V2 uplinks must not evict each other or overwrite fleet status. |
| Provider/account secrets | Separate Deepgram, generic STT, Live, TTS, engine, DL, MQTT and connector references. Imported fallback-to-LLM credentials need review for intended scope and quota coupling. |
| Person identity | Stable ID mapping for face/voice labels, display names, channel identities and historical records. Resolve collisions; keep unknown/unattributed data distinct. |
| Biometric evidence | Preserve private originals, model/preprocessing version, enrollment versus automatic extension provenance and consent. Quarantine incompatible embeddings; no implicit cloud re-enrollment. |
| Persona and memories | Preserve original files and migration conflicts. Split user instructions, learned facts, inferred claims and runtime-specific working state; corrections/deletions propagate to derived context. |
| Logs and derived habits | Preserve dates/timezones, subject/source and uncertainty. Rebuild derived patterns only from compatible data. Apply a privacy/retention policy to debug crops, WAVs and exports too. |
| Schedules and unfinished tasks | Import schedule occurrence identity/timezone/enabled state; reconcile in-flight V1 work before enabling V2 submission. Carry unresolved state as uncertain, not success or automatic replay. |
| Integration trust | Harness seed/peer pin/results, Buddy pairing, messaging and connector credentials require explicit ownership transfer or re-pair. Result/delivery cursors and expiry are part of state, not disposable cache. |
| Body settings | User lighting/volume/scene preferences are separate from transient cues, same-boot mute/sleep markers and physical privacy switch state. The switch remains authoritative after import. |
| Hardware calibration | Copy only with matching unit, board, actuator IDs, schema, units and qualification evidence. Preserve manufacturer calibration/safety profile across owner reset; never copy 4ace's values to another unit. |
| Update/developer state | Preserve trusted signing root and rollback history deliberately. Keep simulator state, fixtures, caches and support bundles out of production identity and the public repository. |

The importer should never overwrite its only source copy. A successful parse is
not a successful migration: compare counts, IDs, consent, resolved settings and
reconciliation results, then exercise the acceptance scenarios with synthetic
data before any authorized real-data cutover.

## Dependency order for the build plan

Build each slice as a complete Rust path with contracts, failure behavior and
verification. Keep V1 as the available production fallback until deliberate
cutover. Compare against V1 using fixtures, simulation or separate hardware;
never run V1 and V2 hardware writers or production uplinks concurrently on the
same unit. Cutover must stop the old owners, reconcile accepted work, transfer
state and then enable the new owners. A migration importer or comparison tool
is temporary support, not a permanent dependency on Go os-server/Python HAL.

1. **Establish contracts and fixtures.** Define typed observations, context
   versions, task/action IDs, admission/results, capability discovery and state
   manifest. Capture synthetic V1 fixtures for the matrix. Keep R ownership,
   observation, camera, ring and motor cores where they already fit.
2. **Make the core Lamp dependable.** Privacy/touch/light, truthful boot/readiness,
   provider failure state, Deepgram fallback and Gemini TTS must survive Live
   exhaustion. Add bounded service supervision, config/auth and operator repair.
   Motion stays disabled unless its selected profile is qualified.
3. **Restore useful agency.** Connect a remote Hermes adapter through the new
   engine contract, typed device tools and durable task journal. Add context,
   memory, corrections and scheduled work. Port relevant V1 skill guidance;
   eliminate loopback/file assumptions in remotely executed tools.
4. **Prove the boundary and integrations.** Qualify a second engine, then Harness
   and selected channels/connectors. Test steering, unclear admission, replay,
   engine restart and result delivery. Evaluate Jev separately for each of its
   four purposes; it is optional selection assistance, not the executor.
5. **Enable qualified senses and behaviors.** Independent sensor workers feed
   current situation state regardless of speech policy. Port local presence and
   useful vision first if camera is selected; add identity/environment as
   selected hardware permits. Defer unqualified emotion/habit/guard initiative
   visibly. Qualify motion before attaching any behavior that invokes it.
6. **Perform an authorized migration and comparative release evaluation.** Run
   dry-run/export/import/rollback/reset scenarios, then matched V1/V2 user tasks
   on the intended physical configuration. Release only the capabilities that
   passed their criteria; retain a documented path for deferred private state.

This order avoids two common false finishes: a fast voice pilot with no durable
tasks/operations, and a broad Rust rewrite that reproduces V1's hidden coupling.
The acceptance unit is a useful, observed user outcome under failure as well as
normal operation.
