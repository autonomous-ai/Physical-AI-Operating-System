# Remaining boundary after the microphone clock preparation

Recorded 2026-10-16 07:48:58 +0700, from shell date. This is a read-only handoff note, not a proposed source change or validation claim.

The reviewed preparation only owns time reads inside `MicrophoneOn`. It leaves `audio_workers::capture_on` at the unchanged ordinary constructor (`audio_workers.rs:346`) and leaves its loop parameter at `MicrophoneOn<D>` (`:383`). It cannot yet advance the original capture-hold scenarios without their real waits.

The next reviewable preparation can observe a completed bounded capture-worker pass while preserving all host time and pacing. Such a receipt must distinguish the actual return paths: the normal tail, capture hold's early continue after accepting a frame, and the authority-stall early continue after the final maintain check. Receipt publication must happen only after that path's real bounded control/reference intake and actual applicable device/processing/channel operations. Successful socket enqueue is not peer consumption; completed device read is not completion of the whole worker pass. A receipt alone grants no permission to advance a clock.

The current capture loop has real host pacing and several time domains: `Instant` for tick/held-up/busy-at-start control, monotonic microseconds for reference/gap/prime checks and reports, and the microphone boundary source. Migration needs explicit admission coordinating all of those policy reads without widening the 2 ms tick, 8-control/16-reference limits, held-up handling, 250 ms authority lease, 10 ms read budget, privacy/age bounds, or capture hold. Transport connection/envelope watchdog time can remain host time only when both peers and their domain distinction are preserved. This clock-only change does not select any of those future designs.

`CaptureStopped` is not thread exit. The Stop arm revokes and sends that event, then `capture_on` still performs `control_lost`, drops the microphone, reports errors and finishes optional recording. A later fixture must own cancellation and actual `JoinHandle` completion, including error/panic paths, under one absolute host watchdog. A callback or result message emitted just before closure return cannot certify actual thread exit. A Rust thread stuck in blocking code cannot be forcefully reaped by timing out its join; bounded cancellation of every fixture-controlled wait or a separately owned child process is needed before claiming that property.

The existing Linux Rig, warm-up attempts and all five original/current capture-hold tests remain untouched. Their real-clock waits, existing assertions and warm-up behavior are recorded in the earlier four-case plan. Any progress or ownership implementation needs its own concrete source review and native Linux qualification; the current Mac boundary gate does not establish it.
